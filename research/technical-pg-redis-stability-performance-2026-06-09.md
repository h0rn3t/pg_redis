## Codebase Analysis — Stability

### Session mode (memory & error paths)

Session mode is the **soundest** of the three. The TLV codec, dynahash entry lifecycle, FLUSHALL-via-context-reset, type-tag validation, and lazy-expiry re-entrancy were all read carefully and found correct (`src/binval.c:115-145`, `src/kv_store.c:54,216`, `src/ttl.c:66`). Two real issues stand out.

The most serious is an **error-path gap in the pre-commit flush** (`src/persistence.c:169,303,327-328`). `run_flush()` is called directly from the `XACT_EVENT_PRE_COMMIT` handler with **no `PG_TRY`/`PG_CATCH`**. Its first act is to take ownership of the dirty-set and pending-deletes (`dirty = pg_redis_dirty_head_take()`, `deletes = pg_redis_pending_deletes_take()`), which null the module-level heads immediately. The live entries still carry `in_dirty_set = true`. Any subsequent `SPI_execute_plan` can `ereport(ERROR)` (unique violation, serialization failure, OOM). On that longjmp the transaction aborts and `XACT_EVENT_ABORT` runs `pg_redis_dirty_clear()`, which walks `dirty_head` — now `NULL` — so the stuck `in_dirty_set = true` flags are **never reset**. Because `pg_redis_mark_dirty` short-circuits on `if (e->in_dirty_set) return;` (`src/kv_store.c:522-523`), those entries are silently never re-enqueued, and their future changes are **never persisted** for the life of the backend. This is silent durability loss. Fix: wrap `run_flush` in `PG_TRY`/`PG_CATCH` that walks the locally-held chains and clears `in_dirty_set`/`dirty_next` (and frees delete nodes) before re-throwing — or defer nulling the heads until the SPI work succeeds.

The second is **signed-integer overflow in INCR/DECR**: `newval = e->value.int_value + delta` (`src/pg_redis.c:571`) has no overflow guard, which is UB at `INT64_MAX`/`MIN` and diverges from Redis (which raises "increment or decrement would overflow"). Use `pg_add_s64_overflow()`.

### Shared mode (DSA, locking, reentrancy)

Several things are **correct**: DSA multi-step builders roll back on OOM via `PG_TRY`/`PG_CATCH` (`src/shared_store.c:187-211,232-245`; `src/shared_hash.c:352-359`; `src/shared_list.c:24-28`); the open-addressing hash table's probe/resize/tombstone logic is sound and resizes only under `LW_EXCLUSIVE`; `pg_redis_shmem_dsa()` pins the area correctly and never caches a raw `dsa_get_address` across a remap; the dirty-ring's per-slot barrier protocol is right. The serious problems are in **lock ordering, the read-modify-write contract, and a few init/encoding gaps.**

**Critical — lock-order inversion + self-deadlock.** There are two acquisition orders for the same two lock classes. Normal writes hold a **partition lock** then, on the first DSA allocation, acquire `startup_lock` (`src/shmem.c:223`): order {partition → startup}. The cold-load path acquires `startup_lock` (`src/persistence.c:1008`) then, inside the loaders, acquires **partition locks** via writeback/upsert (`src/persistence.c:811,854,968`): order {startup → partition}. Two backends running these concurrently can deadlock. Worse, there is a **self-deadlock**: a cold-loading backend holds `startup_lock`, and the first hash/list/string writeback calls `pg_redis_shared_palloc` → `pg_redis_shmem_dsa()`, which (if DSA isn't yet attached — the common case on a fresh backend) does `LWLockAcquire(startup_lock, LW_EXCLUSIVE)` while the same backend already holds it. LWLocks are not reentrant → hang. This is masked only when the durable store is empty (load allocates no DSA), which is why basic tests don't hit it. Fix: attach DSA *before* taking `startup_lock` or any partition lock; never call `pg_redis_shmem_dsa()` while holding a partition lock; establish one global lock order.

**High — the scratch-copy contract loses concurrent updates.** The documented contract (`src/shared_store.h:8-24`) materializes a shared row into palloc'd scratch under the lock, **releases the lock**, lets the caller mutate the scratch lock-free, then re-acquires the lock in `pg_redis_shared_store_writeback`. This is a read-modify-write split across two independent lock acquisitions. INCR/DECR (`src/pg_redis.c:537→571→575`): two concurrent `INCR k` both read the same start value and both write `v+1` — one increment lost. LPUSH/RPUSH/LPOP/RPOP (`src/pg_redis.c:949,1005`): writeback releases and rebuilds the **entire** list from the stale scratch (`src/shared_store.c:586-587`), wiping a concurrent push/pop. Only HSET/HDEL got a correct single-lock atomic path (`pg_redis_shared_hash_set_atomic`/`_del_atomic`). *(This was independently flagged by the performance agent — see below — making it a High-confidence, doubly-confirmed bug.)*

**High — `lock_partitions` not constrained to a power of two.** `ShmemInitHash` is called with `num_partitions = pg_redis_lock_partitions` and `HASH_PARTITION` (`src/shmem.c:157,163`), but the GUC has range 1–128 and **no check_hook / no power-of-two rounding** (`src/pg_redis.c:255-264`). PG18 `hsearch.h:68` requires `num_partitions` to be a power of two, and the partition-lock scheme's correctness depends on `pg_redis_partition_lock`'s index (`hash_bytes % lock_partitions`) matching the dynahash partition index — which holds only when both counts are equal powers of two. A value like 10 or 100 silently breaks the mapping so two keys in different pg_redis partitions can share a dynahash bucket chain and corrupt it.

**High — shared list silently truncates values > 64 KB.** `PgRedisSharedListNode.value_len` is `uint16` (`src/types.h:155`); `new_node` casts the incoming `Size` straight to `uint16` with no bounds check (`src/shared_list.c:36`) while `memcpy`ing the full length. `max_value_size` defaults to 1 MB. A 64 KB–1 MB list element stores full bytes but records `value_len mod 65536` → silent corruption on read. The shared **hash** path guards this (`src/shared_hash.c:279-285`); the list path doesn't.

### Persistence, transactions & crash safety

The core design (dirty-set → batched pre-commit SPI flush via cached `SPI_keepplan` plans → lazy reload on a needs-reload flag) is sound and several failure modes already have `PG_TRY`/`PG_CATCH` guards. The serious problems cluster around **subtransaction/rollback integrity** and a few divergence windows.

**Critical — no `SubXactCallback` is registered; savepoint / subtransaction rollback is completely unhandled.** A grep confirms zero `RegisterSubXactCallback` in the tree. Scenario: `BEGIN; SET a 1; SAVEPOINT s; SET b 2; HSET h f v; ROLLBACK TO s; COMMIT;`. The mutations under the savepoint marked entries into the dirty-set; `ROLLBACK TO s` rolls back nothing in pg_redis, so at COMMIT the flush writes `a`, **`b`, and `h`** durably even though the user discarded `b`/`h`. This fires constantly because **every PL/pgSQL `BEGIN … EXCEPTION` block uses an internal subtransaction** — so any function with an EXCEPTION handler that touches pg_redis can silently persist data from a failed/rolled-back block. *(The best-practices agent independently predicted exactly this failure mode — see "Crash safety" below — high cross-confidence.)*

**High — post-rollback in-memory inserts are never removed.** On top-level ROLLBACK the durable row is dropped and `persistence_loaded=false` forces a reload — but the loader only *adds/overwrites* durable rows, never *removes* in-memory entries with no durable counterpart (`src/persistence.c:704-813`). So `SET k v` (new key) then `ROLLBACK` leaves the in-memory entry alive: `GET k` returns the rolled-back value. The needs-reload flag does not reconcile the insert case.

**High — cached SPI plan slots / static load flags have no teardown** on `DROP EXTENSION` / `DISCARD ALL` / store recreate (`src/persistence.c:51-56,108-131`). (Agent down-rated worst case because PG's saved-plan revalidation likely covers an OID change — confirm empirically.)

Other confirmed issues: a **flush memory leak** — `run_flush` (and the async drain) materialize every value as a fresh `bytea` + text Datum + array in the transaction/executor context with no dedicated MemoryContext, ~doubling peak memory for large transactions (`src/persistence.c:412,447,1290-1394`); **`version` never reloaded** so it rewinds the durable counter on next flush (`src/persistence.c:707-711,818-823,894-900`); **snapshot JSON is not binary-safe** — `escape_json` on raw bytes + `::jsonb` cast throws on non-UTF8 values (`src/persistence.c:1092,1113,1136`); a **HSET→HDEL→HSET ordering hazard** where delete-before-upsert category ordering can durably diverge from the in-memory state (`src/persistence.c:521-558`); a read-path load that hits a corrupt TLV row queues a durable delete (a SELECT mutating durable state, `src/persistence.c:770,787`); and O(deletes×dirty) tombstone-dedup (`src/persistence.c:477-493`).

### Async dirty-ring, background worker & concurrency

The ring's mechanical design (monotonic `fetch_add` write head, per-slot state machine with `pg_write_barrier`/`pg_read_barrier` around the payload) is sound in parts, but there are **two genuinely critical data-loss/corruption bugs** plus a cluster of smaller ones. This is the **least safe** of the three modes.

**Critical — the "single consumer" invariant is not enforced.** Every comment asserts a single consumer (the BGW), and `pg_redis_dirty_ring_drain` relies on it: it reads `read_head` into a local, walks slots, and ends with an **unconditional** `pg_atomic_write_u64(&h->ring_read_head, r)` (`src/dirty_ring.c:209,232`) — no lock, no CAS. But when the ring is full and `async_full_action='sync_flush'`, **any producer backend** drains (`src/dirty_ring.c:144` → `src/persistence.c:1584,1599,1256`). So the BGW and one-or-more producers can be inside the drain simultaneously, partitioning slots via CAS but then each blindly writing its own local `read_head` — the drainer that processed fewer slots **rewinds `read_head`** over slots the other already emptied, wedging the ring and producing duplicate/torn events. Fix: serialize all drainers under a dedicated consumer LWLock (matches the "single logical consumer" intent), or make `read_head` advance monotonically via CAS.

**Critical — slots are freed before the persisting transaction commits.** The drain advances `read_head` and sets each slot `SLOT_EMPTY` *inside the drain* (`src/dirty_ring.c:226-232`), the moment bytes are copied to the caller's buffer. The durable `SPI_execute_plan` runs *afterward* and only becomes durable at the BGW commit (`src/bgworker.c:171`). If anything between drain and commit fails (SPI error, OOM, SIGKILL, crash), the events are **already gone from the ring but never made it to disk** — the whole batch (up to `ASYNC_DRAIN_BATCH_MAX=1024`) is silently lost, with no error to the client (it already returned per the async contract). Fix: advance `read_head`/free slots only *after* the persisting xact commits (two-phase drain, or a post-commit callback).

Other confirmed issues: **over-claim past capacity** — the full-check `w-r < capacity` and the `fetch_add` aren't atomic (`src/dirty_ring.c:130-134` vs `157`), so the per-slot spin can hit the `if (spin >= 1000) ereport(ERROR)` (`src/dirty_ring.c:167-170`) ~10 ms later and **lose the mutation** spuriously; **DSA spill leak** — oversize events allocate a DSA chunk before publish, and if publish ERRORs (full/stuck) the chunk leaks in shared memory forever (`src/dirty_ring.c:315`); **no SIGUSR1/procsignal handler** installed in the BGW (`src/bgworker.c:89-91`) so `CHECK_FOR_INTERRUPTS` may miss procsignal-driven interrupts; **no job-overlap guard** — the same job can run concurrently (BGW tick vs `RUN_JOB`) with no `FOR UPDATE SKIP LOCKED` (`src/jobs.c:223-226`); and the **documented crash window is wrong** — it's bounded by ring fill (up to `dirty_ring_size`, default ~1M), not by `flush_interval`.

**Data-loss scenarios enumerated** (every path where a published mutation never reaches disk): ring full + `block` action → ERROR, mutation rejected but in-memory value already written (divergence); slot-stuck timeout → spurious ERROR; drain succeeds but persisting xact aborts/crashes → whole batch lost; BGW not running → ring fills then rejects; postmaster crash → entire ring lost.

## Codebase Analysis — Performance

### Hot paths, allocations & copy overhead

Session mode is close to optimal (one value copy on SET, no throwaway). **The shared-mode scratch-copy contract is where the waste concentrates** — and it is the *same* contract behind the lost-update correctness bug above, so fixing it pays double.

Shared **GET has no fast path** (unlike HGET): `pg_redis_get` (`src/pg_redis.c:394`) always goes through `materialize_scratch`, which for a STRING does a `palloc0(sizeof(PgRedisEntry))` (>1 KB struct, due to the inline `key[1025]`) plus a shmem→scratch copy under the lock, then `cstring_to_text_with_len` copies *again* into the result — **two full copies + a >1 KB palloc0 per GET**. For a HASH or LIST key it materializes the **entire container** under the lock and then `pg_redis_get` just throws WRONGTYPE — pure waste. Shared **SET takes the partition lock twice** (`materialize_scratch` in upsert, then a full rebuild in `writeback`, `src/shared_store.c:362,534`), needlessly copies the *old* value out, and `pfree`s a throwaway value palloc. There is **no atomic fast path for INCR/DECR, EXISTS, LPUSH/RPUSH/LPOP/RPOP/LLEN, TTL** — all pay the materialize tax; INCR does upsert+writeback = two locks + a copy each way for what should be one exclusive lock + `int_value++`.

### Lock contention & concurrency scaling

Shared **list writeback rebuilds the whole DSA list under the exclusive lock** — every LPUSH/RPUSH re-allocates and re-copies every node, O(N) DSA allocations under lock (`src/shared_store.c:582`). (This is exactly what the in-flight `surgical-list-writeback` change should address — verify.) Async **HSET publishes events while holding the exclusive partition lock**, and `dirty_ring_publish` can spin ~10 ms when the ring is full — so a single backend can hold a keyspace partition lock for ~10 ms, stalling every writer to that partition (`src/shared_store.c:685-698`, `src/dirty_ring.c:128`). The **partition count defaults to 16, capped at 128** — low for many-core write scaling (`src/pg_redis.c:259`). The **partition index is re-hashed multiple times per command** (`%`, not `&`, since not power-of-two) (`src/shmem.c:266,276`).

### Persistence / SPI / dispatch overhead

`ensure_loaded()` runs on **every command** and re-resolves the storage/persistence mode via **`strcmp` on GUC strings 4–6× per command** (`src/utils.c:189`, `src/kv_store.c:496,503,514`) — `storage_mode` is `PGC_SIGHUP` so this is trivially cacheable in an enum. The pre-commit flush **initializes 16 `DatumVec`s (≈32 pallocs) on every commit** even when only one category has work (`src/persistence.c:347-362`), and the **TLV encode allocates a `bytea` + memcpy + pfree per async string SET** purely to build a transient that's memcpy'd again into the ring slot (`src/binval.c:65`, `src/kv_store.c:388`).

## Best Practices (external research)

### PostgreSQL extension memory management & error handling

PostgreSQL's region allocator means **allocate with `palloc`/`palloc0` into a context whose lifetime matches the data; never `malloc`** ([PG18 C-Language Functions](https://www.postgresql.org/docs/current/xfunc-c.html), confidence: High — Primary). Memory freed by `palloc` is reclaimed at transaction end, and destroying a context frees everything in it ([mmgr/README](https://github.com/postgres/postgres/blob/master/src/backend/utils/mmgr/README), High — Primary) — which is exactly why pg_redis's `FLUSHALL` = one `MemoryContextReset`. The load-bearing rule: **a long-lived index must only point at memory in an equally long-lived context**; pointers into a context that's since been reset are the classic crash cause, and "you must be careful to clean up properly during subtransaction abort — the subtransaction's state must be delinked from any pointers or lists kept in upper transactions, or you will have dangling pointers" (mmgr/README, High — Primary). Inside SPI, a pass-by-reference result must use `SPI_palloc` ([PG18 SPI Memory Management](https://www.postgresql.org/docs/current/spi-memory.html), High — Primary).

`ereport(ERROR)` does a **`siglongjmp`** to the nearest `PG_TRY`/`PG_CATCH`, abruptly unwinding the C stack; intervening frames' cleanup never runs ([PG18 Error Reporting](https://www.postgresql.org/docs/current/error-message-reporting.html), High — Primary; [EDB PG_TRY](https://www.enterprisedb.com/blog/postgresql-internals-understanding-exception-handling-pgtrypgcatch), High — Established). It is safe only because resources tie to memory contexts and ResourceOwners that the transaction-abort machinery controls — leaks/crashes come from stepping *outside* that model. PG_TRY rules a reviewer must check: a local modified in TRY and read in CATCH must be `volatile` (or assigned before the TRY); **never `return`/`goto`/`break` out of a TRY or CATCH body** (it leaves `PG_exception_stack` dangling → segfault on the next longjmp); re-throw with `PG_RE_THROW()` and keep CATCH minimal; truly swallowing an error needs a subtransaction (`BeginInternalSubTransaction` + rollback/release), not bare `FlushErrorState`; `PG_FINALLY` auto-rethrows; `FATAL` escapes the construct entirely ([elog.h](https://doxygen.postgresql.org/elog_8h_source.html), High — Primary; [Tom Lane on subtransactions](https://www.postgresql.org/message-id/3353555.1665177543@sss.pgh.pa.us), High — Primary). For destructor-style cleanup of non-palloc resources (DSA handles, files), register a `MemoryContextRegisterResetCallback` (mmgr/README; [mcxt.c](https://doxygen.postgresql.org/mcxt_8c_source.html), High — Primary). Long loops need `CHECK_FOR_INTERRUPTS()`; recursion needs `check_stack_depth()` ([Cybertec: cancel a hanging query](https://www.cybertec-postgresql.com/en/cancel-hanging-postgresql-query/), High — Established).

> These rules directly validate the `run_flush`-no-PG_TRY finding and the missing-SubXactCallback finding above.

### Shared memory, DSA & LWLock discipline

On PG15+ (so PG18) an extension **must size shared memory in a `shmem_request_hook` and allocate in a `shmem_startup_hook`** — calling `RequestAddinShmemSpace`/`RequestNamedLWLockTranche` from `_PG_init` aborts startup; both hooks must chain the previous handler ([pgPedia](https://pgpedia.info/s/shmem_request_hook.html), High — Established; [pg_stat_statements REL_18_STABLE](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/contrib/pg_stat_statements/pg_stat_statements.c), High — Primary). The init-once race is solved with `AddinShmemInitLock` + the `found` flag, not by assuming single-threaded startup. **`ShmemInitHash` directories are fixed-size** — they can't grow, so size `max_size` generously; for partitioned tables `nbuckets` must be ≥ `num_partitions` ([dynahash.c](https://github.com/postgres/postgres/blob/master/src/backend/utils/hash/dynahash.c), High — Primary). With **DSA, store `dsa_pointer` offsets, never raw pointers, and never cache `dsa_get_address()` across an allocate/free/grow** ([dsa.c](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/utils/mmgr/dsa.c), High — Primary); `dsa_allocate` raises ERROR on OOM unless you pass `DSA_ALLOC_NO_OOM`.

The central LWLock facts: **LWLocks are NOT reentrant** — re-acquiring one self-deadlocks, and there is **no production deadlock detector** for them (only under `--enable-cassert`); the canonical footgun is `ereport(ERROR)` while holding one triggering cleanup that re-acquires it ([LWLock self-deadlock thread](https://www.postgresql.org/message-id/CAGRY4nyyYarrwfc72gp5uDyA-wR+Tf6f9YnPhqDv_rw7R5oEYA@mail.gmail.com), High — Primary). **Lock multiple partitions in partition-number order**, and never hold an LWLock across a kernel call or SPI ([lmgr/README](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/storage/lmgr/README), High — Primary). Crucially: **LWLocks auto-release during elog recovery** (so raising an error while holding one is safe), **but spinlocks do not, and DSA allocations are not freed by abort** unless owned by a resource owner — so an ERROR between `dsa_allocate` and publishing the pointer permanently leaks; multi-step builders must `PG_TRY` + `dsa_free` partial work (lmgr/README + dsa.c, High — Primary). Prefer locks over raw atomics; if you use `pg_atomic_*`, pair them with the right barrier (`pg_read_barrier`/`pg_write_barrier`/`pg_memory_barrier`), and note a failed CAS on ARM may leave only a one-way barrier ([atomics.h](https://raw.githubusercontent.com/postgres/postgres/master/src/include/port/atomics.h), High — Primary).

> These validate the lock-order/self-deadlock, DSA-leak-on-publish, power-of-two-partitions, and async-publish-under-lock findings.

### Extension performance tuning & benchmarking

Bulk-free by resetting a context rather than per-`pfree`; **size hot structs just under a power-of-two** (AllocSet rounds up — 1025 bytes wastes nearly half a 2 KB chunk) and use slab/dense allocation for many same-lifetime objects ([pgaddict palloc overhead](https://blog.pgaddict.com/posts/palloc-overhead-examples), Medium — Established). dynahash growth is cheap for palloc-backed (session) tables but **effectively fixed-size for `ShmemInitHash`**, so the shared keyspace estimate matters most (dynahash.c, High — Primary). For SPI: **cache the plan** (`SPI_keepplan`, what persistence.c does) and **batch rows into one `SPI_execute_plan` via array parameters** — UNNEST array-form measured **2.13× faster than per-row INSERT at batch 1000** ([TigerData](https://www.tigerdata.com/learn/testing-postgres-ingest-insert-vs-batch-insert-vs-copy), Medium — Established, single source); for large bulk flushes, **COPY / `heap_multi_insert`** beats batched INSERTs because it uses the WAL multi-insert record (~25 bytes/tuple smaller) and skips parse/plan ([PG18 Populating a Database](https://www.postgresql.org/docs/current/populate.html), High — Primary). Declare hot functions `STRICT`; use `PG_GETARG_TEXT_PP` + `VARDATA_ANY`/`VARSIZE_ANY_EXHDR` to avoid detoast/copy; use `DirectFunctionCall` to skip catalog lookup (PG18 xfunc-c, High — Primary). Benchmark with `pgbench -f -n -r`, `perf record --call-graph dwarf` + flame graphs, and differential flame graphs for before/after ([PG wiki perf](https://wiki.postgresql.org/wiki/Profiling_with_perf), High — Established).

On **prior art**: the strongest tailwind for pg_redis's in-process design is that the usual "Postgres-as-cache" overhead is dominated by network RTT (~1 ms inter-host vs ~0.1 ms cached lookup) and WAL/MVCC — CYBERTEC's point is that in-memory advantages "largely evaporate over a real network" ([CYBERTEC](https://www.cybertec-postgresql.com/en/postgresql-vs-redis-vs-memcached-performance/), Medium — Established, via search snippet). By living in-process, pg_redis eliminates the RTT *and* the RESP/socket layer, leaving WAL and MVCC as the residual costs the dirty-set/async design targets. ⚠️ All cross-source Redis-vs-PG benchmark ratios vary wildly by methodology (60× vs 1.9×) — treat as directional only.

### Crash safety, transaction integration & testing

The **load-bearing ordering rule**: `XACT_EVENT_PRE_COMMIT` fires *before* `RecordTransactionCommit()` while the transaction is still abortable; `XACT_EVENT_COMMIT` fires *after*, in cleanup guarded by "if an error is raised here, it's too late to abort" ([xact.c](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/access/transam/xact.c), High — Primary). So **do all fallible work (SPI flush) in PRE_COMMIT** (pg_redis does — correct), and make COMMIT/ABORT callbacks **resource-cleanup-only and non-throwing**; never call `SPI_commit`/`SPI_rollback` from a xact callback ([spi.c](https://doxygen.postgresql.org/spi_8c.html), Medium — Established). **`RegisterSubXactCallback`** with `SUBXACT_EVENT_ABORT_SUB` is the documented mechanism to undo per-subxact state — and "every PL/pgSQL block with an EXCEPTION clause opens a subtransaction... so savepoint-driven rollback fires constantly" ([CYBERTEC subtransactions](https://www.cybertec-postgresql.com/en/subtransactions-and-performance-in-postgresql/), Medium — Established). The established pattern for an in-memory tier is to mark "needs reload" on ABORT so the next access re-reads the authoritative durable view ([postgres_fdw connection.c](https://github.com/postgres/postgres/blob/master/contrib/postgres_fdw/connection.c), High — Primary/Established). Treat **shared-memory / async tiers as volatile** — unlogged data is truncated by crash recovery; only a clean shutdown preserves it ([Crunchy: Unlogged Tables](https://www.crunchydata.com/blog/postgresl-unlogged-tables), High — Established).

Testing maps onto the existing harness: **pg_regress** for deterministic single-backend SQL; **TAP (`PostgreSQL::Test::Cluster`)** for multi-backend + **crash/recovery** (kill -9, restart, assert WAL-backed rows survived) + BGW behavior; **isolation tester** (`specs/*.spec`) for the shared/async concurrency — note it only auto-detects *heavyweight* lock blocking, not LWLock/spin waits ([isolation README](https://github.com/postgres/postgres/blob/master/src/test/isolation/README), High — Primary). For memory bugs, build PG **and** the extension with matching instrumentation: Valgrind via `-DUSE_VALGRIND` + `MEMORY_CONTEXT_CHECKING`, or **AddressSanitizer** (`CC=clang -fsanitize=address`, `ASAN_OPTIONS=abort_on_error=1`) — PG reuses the Valgrind hooks for ASan ([PG Valgrind wiki](https://wiki.postgresql.org/wiki/Valgrind), High — Primary; [EDB ASan](https://www.enterprisedb.com/blog/stack-buffer-overflow-exercise-addresssanitizer-and-postgresql), High — Established). **Fuzz** the binary `binval.c` codec with libFuzzer (ASan build) and exercise the SQL surface with SQLsmith. CI: a **PG-version matrix** via `pgxn/pgxn-tools` (`pg-build-test`), plus dedicated ASan/Valgrind, isolation, and crash-recovery jobs ([Just a Theory: GH Actions](https://justatheory.com/2020/06/test-extensions-with-github-actions/), High — Established).

## Key Findings

**1. The shared/async modes carry the stability risk; session mode is comparatively solid.** Reading all three implementations, session mode had one real bug (the `run_flush` error path). Shared mode has a self-deadlock and a lost-update class; async mode has two independent critical data-loss/corruption bugs. This is unsurprising — concurrency and lock-free code is where defects concentrate — but it means *"make it stable"* is largely *"harden shared + async, or scope them explicitly."* (Evidence: the four code sections above, `file:line` throughout.)

**2. One root cause drives both a stability bug and the dominant performance waste: the two-phase scratch-copy contract.** In shared mode the read-modify-write is split across two separate lock acquisitions, which (a) loses concurrent INCR/list updates — a correctness violation for the mode whose entire purpose is cross-backend consistency — and (b) forces a >1 KB `palloc0` + double value copy + double lock on the hot path. The performance and stability agents flagged this independently. The fix is the same for both: single-lock atomic command paths, exactly as the existing `pg_redis_shared_hash_set_atomic` already demonstrates (`src/shared_store.c:618`).

**3. Transaction-rollback integration is incomplete, and the gap is invisible until it corrupts durable state.** No `SubXactCallback` is registered, so any PL/pgSQL `EXCEPTION` block (extremely common) that touches pg_redis silently persists data the user rolled back; and post-top-level-rollback in-memory inserts are never reconciled so reads return rolled-back values. The best-practices research predicted this exact failure mode from first principles, raising confidence. This affects **all three modes** because the dirty-set is per-backend (`src/persistence.c`, no `RegisterSubXactCallback` in tree).

**4. Error paths systematically leak or wedge state.** Three independent instances — `run_flush` without `PG_TRY` (durability wedge), the DSA spill leak when publish ERRORs, FLUSHALL holding all locks across SPI — all match the canonical PostgreSQL hazard the research describes: an `ereport(ERROR)` longjmps past your cleanup unless the resource is tied to a context/ResourceOwner or guarded by `PG_TRY`. A single focused pass — *"audit every `ereport(ERROR)` reachable while holding a lock, after taking ownership of a list, or after a bare `dsa_allocate`"* — would catch this whole class.

**5. The async crash window is much larger than documented, and the durability contract is under-specified.** CLAUDE.md/README say "bounded by `flush_interval`," but the ring frees slots before the persisting transaction commits and the window is really bounded by ring fill (up to ~1M events) plus the drain-then-crash gap. For a feature whose selling point is bounded durability loss, this is a documentation *and* correctness issue.

## Strategic Recommendations

Ranked by impact, stability-weighted. Phase 1 is correctness (do first); Phase 2 is performance (mostly free once Phase 1's atomic paths exist).

1. **Fix transaction/rollback integrity (all modes).** Register a `SubXactCallback` that discards dirty-set/pending-delete entries accumulated in an aborted subxact; on top-level ABORT, reset (or reconcile) the in-memory keyspace so rolled-back inserts disappear; wrap `run_flush` in `PG_TRY`/`PG_CATCH` that clears `in_dirty_set` on error. *Rationale:* silent durable corruption from a universally-used SQL construct (EXCEPTION blocks) is the worst failure a "stable" store can have. *Evidence:* `src/persistence.c` (no SubXactCallback), `src/persistence.c:169,303`; corroborated by [xact.c](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/access/transam/xact.c) and [CYBERTEC subtransactions](https://www.cybertec-postgresql.com/en/subtransactions-and-performance-in-postgresql/).

2. **Fix the async dirty-ring, or gate `async_table` as experimental until fixed.** Serialize all drainers under a dedicated consumer LWLock; make the drain two-phase so `read_head`/slot-free happen only *after* the persisting transaction commits; make slot claim a conditional CAS; wrap the spill encode→publish in `PG_TRY` to free the DSA chunk on error. *Rationale:* two independent critical data-loss/corruption paths; the mode is currently unsafe for production durability. *Evidence:* `src/dirty_ring.c:197-235,226-232,130-157,315`.

3. **Fix shared-mode lock ordering and the partition GUC.** Attach the DSA segment before taking `startup_lock` or any partition lock; establish and document one global lock order (ascending partition index); never call `pg_redis_shmem_dsa()` while holding a partition lock; add a `check_hook` forcing `lock_partitions` to a power of two and assert it equals the HTAB partition count. *Rationale:* a latent self-deadlock that only hides because test stores are empty at cold-load. *Evidence:* `src/shmem.c:223`, `src/persistence.c:1008`, `src/pg_redis.c:255-264`; corroborated by [lmgr/README](https://raw.githubusercontent.com/postgres/postgres/master/src/backend/storage/lmgr/README) and [hsearch.h:68].

4. **Replace the two-phase scratch contract with single-lock atomic command paths** for GET, SET, INCR/DECR, EXISTS, and list push/pop — mirroring the existing atomic HSET/HDEL. *Rationale:* this is the single highest-leverage change — it eliminates the lost-update correctness bug (#2/Finding 2) *and* the dominant shared-mode performance waste (double copy, double lock, >1 KB palloc0) in one move. *Evidence:* `src/shared_store.c:362,534,618`, `src/pg_redis.c:394,524`.

5. **Close the remaining data-integrity gaps:** guard shared-list values > 64 KB (`src/shared_list.c:36`); restore `version` on reload; make snapshots binary-safe (base64/hex, not JSON-on-bytes); fix the HSET→HDEL→HSET tombstone ordering; add the INCR overflow guard. *Rationale:* each is a silent-corruption or divergence bug; individually small, collectively they undermine trust in the store.

6. **Performance pass (after Phase 1):** cache the storage/persistence mode in an enum via `assign_hook` (kills `strcmp` 4–6×/command); implement surgical single-node list append (the in-flight `surgical-list-writeback` change — verify it lands); move async event publish outside the partition lock; raise the `lock_partitions` default/cap; give the flush its own `MemoryContext`; lazy-init the DatumVecs. *Rationale:* low-risk, high-frequency wins; several also shorten lock hold time, helping stability under contention. *Evidence:* the performance table above.

7. **Build the verification harness that locks all of this in.** Add isolation tests (`test/async/*.spec`) for concurrent INCR (lost update), the cold-load deadlock, and savepoint rollback; a TAP crash-recovery test (kill -9 → restart → assert WAL-backed survival + correct reload); ASan and Valgrind CI jobs (PG + extension built with matching instrumentation); and a libFuzzer harness over `binval.c`. *Rationale:* every finding here is static-only; without tests these bugs (and their fixes) will silently regress. *Evidence:* [isolation README](https://github.com/postgres/postgres/blob/master/src/test/isolation/README), [PG Valgrind wiki](https://wiki.postgresql.org/wiki/Valgrind), [EDB ASan](https://www.enterprisedb.com/blog/stack-buffer-overflow-exercise-addresssanitizer-and-postgresql).

## Risks and Uncertainties

- **All codebase findings are static-analysis only** — no build, run, or profiling was performed. The critical concurrency bugs (cold-load deadlock, lost updates, ring rewind) are timing-dependent; reproduce them with isolation/stress tests before and after fixing. Treat severities as well-reasoned-from-code, not empirically measured.
- **SPI plan revalidation** (the cached-plan teardown finding) depends on whether PostgreSQL's saved-plan revalidation fires for these specific plans on a `DROP`/recreate of `pgredis.store` — confirm empirically; the worst case (stale-OID execution) may not be reachable.
- **The performance impact ratings are reasoned, not profiled.** Run `make docker-bench` and `perf` flame graphs to rank them; the shared-GET/INCR fast paths are the most confident wins but the numbers are unverified.
- **Web benchmark numbers are low-rigor and conflict** (Redis-vs-PG ratios span 1.9×–60× by methodology). They are used only to characterize *sources* of overhead (network, WAL, MVCC), not to predict pg_redis's numbers — and no published benchmark exists for a *truly in-process* Redis-in-PG, so `make docker-bench` is your only direct measurement.
- **In-flight OpenSpec changes overlap these findings** (`fix-crash-safety`, `harden-shared-memory-error-paths`, `surgical-list-writeback`) but were not read. Before implementing, check what they already cover to avoid duplicate or conflicting work — especially whether `fix-crash-safety` includes the SubXactCallback and the async two-phase drain.
- **PG18 API specifics** (e.g. whether `GetNamedDSA`/`GetNamedDSHash` ship in your exact 18 minor) were flagged uncertain by the research; verify against installed headers before adopting newer shared-memory APIs.
